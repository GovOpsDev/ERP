# Organization-aware user roles

## Implemented

`erp_user_role` depends on `erp_organization`, not HR. `erp.user.role` is company-owned and has a unique code per company, name, active flag, description and direct group mapping. `erp.user.role.assignment` separately records user, role, company, optional unit, active flag and inclusive dates. User organization assignments describe where the user may operate; role assignments describe capabilities. There are no global role definitions. A unit assignment requires an active matching organization assignment at creation or relevant scope changes; it must match the role and assignment company and the user's allowed companies. Portal users are rejected. An unscoped assignment is available only to a security administrator.

`fields.Date.today()` supplies a single **server-local date** independent of the viewer's timezone. Both dates are inclusive. A role assignment contributes only while it and the role and user are active, the user still has the company, the dates include today, and any unit is active and still assigned to the user. Revocation of an organization assignment, or archive of its unit, immediately stops that unit's contribution without deleting role history. Restoring the organization assignment or unit reconciles again. Role archive similarly stops contribution. Editing role groups, changing an assignment, and changes to a user's active state or allowed companies reconcile affected users in the same transaction.

One hourly scheduled action reconciles users with role assignments or tracked group states to apply date transitions. It is idempotent on unchanged membership. Transition latency can exceed an hour if the scheduler is delayed or unavailable: do not rely on it for instantaneous expiry. It scans all such users each run and has not been load-tested. Security-sensitive expiry needing an exact deadline needs a different enforcement mechanism.

## Membership provenance

`erp.user.role.group.state` is internal bookkeeping for each user and directly mapped group while any role needs it. A database row lock per affected user serializes reconciliation and ORM group membership writes. The engine computes the union of mapped groups across all effective assignments and links only missing `res.users.group_ids`; it never replaces the user's entire group set. The `manual` state is set if the direct link already existed at first reconciliation, or when a later ORM write explicitly links or retains it. Both `res.users.group_ids` and inverse `res.groups.user_ids` writes are observed, including link, unlink, clear and set commands. A set operation conservatively treats each included group as an independent retain request, including a no-op retain. When a direct link is explicitly removed while a role still requires it, reconciliation restores the link and removes manual protection.

When the last role ceases to require a group, the engine unlinks the direct membership only if its state is not protected as manual. If another role needs the group, the group and state stay. Odoo computes implied groups from `res.groups.implied_ids`; the engine never adds or removes the implied closure. A manual or other direct parent can still imply a child after the role-owned parent is removed.

The conservative retain rule can keep a permission after all roles end if a bulk set from an administrator or another addon retained the group; an administrator must remove it explicitly if that was not intended. Direct SQL, direct relation-table writes, or code bypassing the ORM hooks cannot convey provenance; such integrations are unsupported and must not be used to manage these groups. Tracking uses an internal Python context variable, not a caller-provided Odoo context flag. The design is not an immutable audit log; standard Odoo create/write metadata and group-change logs apply.

## Delegation and boundaries

Odoo Settings administrators (`base.group_system`) create and archive role definitions and configure explicit delegation records. A delegation identifies a manager, role and unit; its company is derived from the role and must match the unit and the manager's allowed companies. The separate Role Assignment Manager group gives no business role groups. A manager may create, change or delete only assignments covered by an explicit delegation in an active company, and may not assign to themselves or make unscoped assignments. Destination and original scope are checked on changes. Possession of a business group does not imply permission to delegate it. A separate administrator-created definition delegation names the manager, role and permitted groups. The manager can edit metadata and map only groups on that allowlist, in an active company; group mapping changes are rejected whenever the role has any assignments, including inactive ones. A row lock serializes this check with assignment foreign-key insertion. Only Settings administrators can create roles, manage delegation or change group mappings on assigned roles. Privileged groups are never preapproved: an administrator must deliberately include them in a definition delegation or an assignment delegation. Administrators must review the full implied-group closure as well as each explicit group, because allowing a parent also allows all capabilities it implies. Managers cannot change role company or active state. Creating and archiving roles through delegated managers is deferred.

**Odoo group membership is global per user.** A company or unit on an assignment qualifies whether the role contributes a capability; it does not scope the capability to that company or unit. Business models must independently enforce company and organization record rules. Do not treat this addon as business-domain data isolation.

## Upgrade and remaining limits

Installation creates no roles, role assignments or conversion of existing groups. Existing direct groups are not swept. Migration of NSTDA role data is a separate future process. Role grants can affect every installed application; test each application's security before rollout. Browser UI, scheduler execution at real time, concurrent transactions, large-scale performance, uninstall, production data migration, complete HR surfaces and other business applications remain unverified. See `user-role-test-report.md` for the scope actually tested. The Organization migration remains **PARTIAL**.

Employee primary/additional organization membership is independent of role assignment and user OU assignment. Employee membership edits do not automatically create or revoke roles or group grants. The proposed cross-domain contract is in `employee-multi-organization-design.md`.
